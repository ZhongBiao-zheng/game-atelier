# 宿主内置节点借用插件节点外壳

2026-11-15 加入「分镜」节点时，画布文档的节点类型是封闭联合，所有模型 `extra="forbid"`。新增一个节点类型会让旧版本读不出整份文档；安装包有应用内更新与回滚（ADR-0030），回滚后的旧版本会读到新版本写的文档。

## 实测（v5.137.0 后端，隔离数据目录，两个项目）

| 存法 | 项目列表 | 其它项目 | 含新节点的项目 |
|---|---|---|---|
| 新节点类型 `type: "storyboard"` | 接口不报错，但该项目从首页项目列表里消失（`list_canvas_projects` 跳过校验失败的项目） | 正常 | 打开返回 422，正文是 Pydantic 英文原文 |
| `type: "plugin"` 外壳，数据放 `payload` | 两个项目都在 | 正常 | 正常打开，节点显示占位「插件节点」；旧版本里改别的节点并保存后，`payload` 与原来完全一致 |

另一条实测结论：v5.137.0 拒绝任何连到插件节点的连线（整份文档 422）。

## 决策

- 宿主内置、且需要自己保存结构化数据的新节点，存成插件节点：`type: "plugin"`，`plugin_id` 用保留前缀 `atelier.`，数据放 `payload`。分镜节点是 `atelier.storyboard` / `node_type: "board"`。以后新增内置节点类型优先沿用这种存法；只有旧版本读不出也可以接受时才新增联合成员。
- `atelier.` 前缀保留给宿主。插件 id 的格式是 `^[a-z][a-z0-9-]{1,39}$`，不允许 `.`，所以任何插件包都取不到这类 id；这条由测试固定。
- 保留前缀的节点由宿主直接渲染，不经过插件注册表、项目批准与沙箱。因此 `payload` 必须当作不可信数据（项目包导入、局域网分享、复制粘贴都可能带来别人构造的内容）：
  - 只通过宽容的解析函数读取，每个字段都有类型、长度与数量上限；缺字段补默认，多余字段丢弃。
  - 文字只作为文本渲染，不用 `dangerouslySetInnerHTML`。
  - `payload` 里的节点 id 只在当前文档内解析，指向不存在或类型不符的节点时当作没有。
- 读盘模型对 `payload` 只保留现有的 256 KiB 大小约束，不加形状校验。形状规则放在解析函数里（前后端各一份，共用夹具 `tests/fixtures/storyboard_payload_cases.json`），以后调整字段不会让旧文档读不出。
- 这类节点不接连线。需要引用别的节点时把 id 存在 `payload` 里。

## 分镜节点

- `payload`：画幅、风格前缀、角色与场景条目、有序镜头、剧本来源文本节点的 id。镜头的图片与视频是画布上的普通节点，镜头只保存它们的 id。
- 上限 120 镜、60 个条目；写入前检查序列化大小，超过时不写入并提示拆成两个分镜节点。
- 复制粘贴：绑定的节点一同被复制则改指新节点，否则清空。项目包原样携带。
- 画布 Agent 的 `get_canvas` 对分镜节点额外输出只读的镜头摘要；本期没有写镜头的 Agent 工具。

## 没有采用

- 新增节点类型并接受旧版本读不出：项目会从列表消失，报错不可读。
- 数据放项目目录下的独立文件、节点只留外壳：外壳同样只能是插件节点，另存文件会让撤销重做、复制粘贴、项目包、同步快照各多一条路径。

## 后果

- 旧版本打开含分镜节点的画布时，节点显示占位，数据保留；镜头的图片、视频节点照常可用。
- 宿主里处理插件节点的代码要先判断保留前缀，再走插件路径。
- 单个内置节点的数据受 256 KiB 约束。
