# Studio / Canvas 功能交付

适用于共享资产、跨 Studio/Canvas 交互及领域对象变更。单点 Bug、文案和样式微调不要求额外 PRD 或原型。

## 开发前

- 先确认对象归属，以及创建、编辑、使用、删除的语义；未确认前不写完整生产实现。
- 对照当前任务范围；日常开发统一在 `dev`，保留已有未提交与未推送工作。若与其他任务改动重叠，先协调，不擅自覆盖或吸收既有未合并分支。
- 涉及高风险交互时，先在真实页面位置验证最小流程，再扩展到另一界面；已有明确规格不重复询问。

## 跨界面检查

- Studio 与 Canvas 使用同一资产来源；区分“复制内容”与“持续引用”，检查编辑、使用、删除后的两端结果。
- UI 改动实测相关的加载、错误、hover、focus、disabled、长文本与多标签状态。
- 反馈改变对象或操作语义时，先确认新规则，再同步实现、测试和项目文档；不把领域变化当成删除按钮。

## 文档边界

- 长期产品事实写入 `CONTEXT.md`；接口契约写入 `docs/api-contract.md`；难以逆转的决策写入 `docs/adr/`。
- PR 描述记录当前问题、范围、规则变化与验证结果；不能只链接接手者读不到的本地文件。
- 草稿、PRD 推演、执行日志放在本地 `.scratch/<feature>/`，默认不提交；交付前把必要结论提炼到项目文档。
- 个人 Agent 偏好与通用方法论不在本仓库重复维护。

## 交付

- `make verify`：lint、测试、干净构建、插件和路径检查；先暂存预期的 `web/dist`，再验证重建无差异。
- UI 功能还需真实浏览器验证；文档检查与测试通过不能代替界面验收。
- 日常完成后提交并推送 `dev`，不自动更新 `main`。
- 用户明确要求“同步”或指定本次合入 `main` 后，核对 PR 范围、最新产品规则和 CI，再合并。
- 同步后更新 `main`，保留 `dev` / `main` 两个长期分支，回到 `dev` 继续开发；保留其他未合并工作。
