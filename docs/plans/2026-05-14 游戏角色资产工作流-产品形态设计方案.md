## 0. 一句话决定

**Skill 内核 + 本地 Web UI**，B 起步（Web 只读看图，2-3 天）→ C 落地（Web 主交互，再加 2-3 周）。

- Skill 跑在画师自己的 Claude Code 里（用画师自己的 Claude 账号 / 额度）
- 本地 Web UI 是 Skill 启动的伴生窗口，localhost，无服务器、无云、无账号
- 文件系统是唯一 source of truth；图片不进 Git，存到画师本地可选的文件夹

---

## 1. 评估了哪些候选方案

| 维度 | **A. 纯 Skill / CC 对话** | **B. Skill 主 + 只读 Web UI** | **C. Web UI 主 + Skill 后端** | **D. 桌面 GUI App**（Tauri/Electron） |
|---|---|---|---|---|
| **画师入口** | VS Code / CC 终端 | 终端聊天 + 浏览器看图 | 浏览器 | 双击桌面图标 |
| **看图怎么解决** | Finder / PS / VS Code 预览 | Web 渲染、对比 | Web 渲染 | App 内置 |
| **改 prompt 在哪** | 聊天里 | 聊天里 | Web 表单 + 聊天 | App 表单 |
| **聊天在哪** | CC 终端 | CC 终端 | Web 聊天框 | App 聊天框 |
| **Skill 可移植性** | ✅ 任意 agent host | ✅ 仍可移植 | ✅ 仍可移植 | ❌ Tauri 绑死 |
| **画师心智门槛** | 高 | 中 | 低 | 最低 |
| **开发代价（模型执行单位）** | 0 | 2-3 天 | 2-3 周 | 3-4 周 |
| **服务器 / 账号** | 无 | 无（localhost） | 无（localhost） | 无 |
| **未来 SaaS 演化** | 要重写 UI 层 | 要重写主交互 | 天然支持 | 桌面 App 推倒 |

**选择 B 起步 → C 落地的理由**：

1. **A 直接淘汰**：画师明确说"还是需要能直观地看到出来的图片"，A 的"丢路径让画师用 Finder 开"违反硬要求。
2. **D 直接淘汰**：桌面 App 把 Skill 内核绑死在一个 shell 里，丢掉"可装在 CC / OpenClaw / Codex 等多 host"的便携性——这条是架构哲学锚，不为 UI 心智门槛松绑。
3. **B 是当下杠杆最高**：用 2-3 天解决"看图"硬伤，主交互仍是 Skill。
4. **B 是 C 的踏板**：B 的 localhost server + 图片渲染前端是 C 的子集，C 只在它上面加"写接口 + 文件输入队列 + 实时推送"。
5. **C 是未来 SaaS 的天然预演**：架构（Web 前端 + Skill 后端）从 localhost 搬到云端是换部署位置，不是重写产品。

## 2. 整体架构

### 2.1 B 阶段（V1，2-3 天）：Skill 主交互 + 只读 Web 镜像

```
┌──────────────────────────────────────────┐
│ 画师本人电脑（PC 或 Mac）                  │
│                                          │
│  ┌──────────────────┐  ┌──────────────┐  │
│  │ Claude Code      │  │ 浏览器        │  │
│  │ （画师自己账号）  │  │ localhost     │  │
│  │                  │  │ :5173         │  │
│  │  character-      │  │               │  │
│  │  workflow skill  │─→│ 只读 Web UI   │  │
│  │                  │  │ 图廊 / 进度    │  │
│  └──────────────────┘  └──────────────┘  │
│        │                      ↑          │
│        ▼                      │          │
│  ┌──────────────────────────────────┐   │
│  │ 本地文件系统（source of truth）   │   │
│  └──────────────────────────────────┘   │
└──────────────────────────────────────────┘
```

**关键约束**：
- 文件系统是唯一数据源，Web 只读
- 画师所有写操作（说"再朴素一点"、改 prompt）仍走终端聊天
- Web Server 启停由 Skill 一句话控制

### 2.2 C 阶段（V2，再加 2-3 周）：Web UI 升为主交互

```
┌──────────────────────────────────────────┐
│ 画师本人电脑（PC 或 Mac）                  │
│                                          │
│  ┌──────────────────┐  ┌──────────────┐  │
│  │ Claude Code      │  │ 浏览器(主)    │  │
│  │ （画师自己账号）  │←─│               │  │
│  │  character-      │  │ Web UI        │  │
│  │  workflow skill  │  │ 聊天+看图+编辑 │  │
│  │                  │─→│               │  │
│  └──────────────────┘  └──────────────┘  │
│        │     ↑                ↑          │
│        ▼     │                │          │
│  ┌──────────────────────────────────┐   │
│  │ 本地文件系统（source of truth）   │   │
│  │  + .runtime/inbox/（输入队列）    │   │
│  └──────────────────────────────────┘   │
└──────────────────────────────────────────┘

【回合制】画师在 Web 改 → 文件落盘 → 回 CC 输"继续" → Skill 读取继续执行
```

**关键约束**：
- **Skill 不是 Web Server 去 spawn 的**，而是跑在画师自己登录的 Claude Code 里。Web Server 只读写文件，**不调任何 Claude API**。
- **回合制衔接**：画师 Web 提交后回 CC 输"继续"。剪贴板自动复制"继续"。
- Skill 内核相对 B **零修改**，仍以"读文件、调工具、写文件"工作。

## 3. B 阶段具体范围（V1，2-3 天）

> **关于技术栈**：本设计是 stack-agnostic。Web Server 用 Node 还是 Python、前端用 React 还是 Vue、文件监听用 chokidar 还是 watchdog——这些都不锁死在设计层，留给 writing-plans 阶段基于实施者的便利度和团队倾向定盘。

### 3.1 交付物清单

| # | 组件 | 内容 |
|---|---|---|
| 1 | **localhost web server** | 单文件 Node script（或 Python FastAPI），默认端口 5173，启停由 Skill 控制 |
| 2 | **文件监听** | 监听 `<image_storage_root>/` 新文件、`.runtime/jobs/*.json` 状态变更 |
| 3 | **只读 API（3 个端点）** | `GET /jobs`、`GET /images?character=<id>`、`GET /spec/<character_id>` |
| 4 | **前端单页（最简 React 或 Vue）** | 三栏：左 = 任务进度，中 = 图廊缩略图网格，右 = 当前选中图大图 + prompt/档案预览 |
| 5 | **首次启动配置页** | 让画师选 / 粘贴图片存储目录，写入 `.runtime/config.json` |
| 6 | **Skill 端集成** | 新增 mini-skill `viewer-server`：`start` / `stop` / `open-browser`；image-gen 在生成完图后写一条 `jobs/*.json` |
| 7 | **画师指南** | `docs/画师上手指南.md` 加一节"打开看图面板"，含截图 |

### 3.2 画师 B 阶段的实际操作

```
画师（终端）：我要做暗影刺客女角色
Skill：[问几个问题 → 生成 characters/shadow_spear_warrior.md]
画师：出一张站桩立绘
Skill：[生成 prompt，展示] → 准备出图，确认？
画师：确认
Skill：[调 Lovart → 4 张 PNG 落到 <image_storage_root>/ → 写 jobs/job-001.json]
       好了，打开看图面板？(y/n)
画师：y
Skill：[启动 web server, 弹浏览器]
画师：[浏览器里 4 张图缩略图 → 点开第 2 张大图 → 旁边显示当前 prompt]
画师（回终端）：这把矛太花，再朴素一点
Skill：[重写 prompt → 展示 → 出图 → web 自动刷新]
```

**画师"写"的动作仍 100% 在终端**。Web 是观察窗。

### 3.3 显式不做（B 阶段）

| 不做 | 原因 |
|---|---|
| Web 上点"重出"按钮 | 引入"Web → Skill 反向通信"，B 就变 C 了 |
| Web 上编辑角色档案 | 同上 |
| 多用户 / 账号 / 鉴权 | localhost 只有画师本人开，没需求 |
| 图片精细对比（slider / 重叠） | 缩略图 + 大图够 V1 验证，复杂对比留 V2 |
| 历史版本回溯 UI | Git 已经够了 |
| 任何 SSE/WebSocket | 前端 `setInterval(2s)` 轮询 `/jobs` 即可，省一层基础设施 |

## 4. C 阶段具体范围（V2，再加 2-3 周）

### 4.1 相对 B 的"加法清单"

| # | 组件 | 新增内容 | B 的复用 |
|---|---|---|---|
| 1 | Web Server 升级 | 加写接口 `POST /spec`、`POST /prompt`、`POST /inbox`，都只落到本地文件 | 复用 B 的文件监听、只读 API |
| 2 | 输入队列文件 | `.runtime/inbox/<timestamp>.md`：画师在 Web 提交的内容写到这里，Skill 下次跑时按时间序读取 | B 没有 |
| 3 | 回合衔接 UX | Web 上每次"提交"后弹一句"已写入，请回 Claude Code 输入'继续'"；剪贴板自动复制 | B 没有 |
| 4 | Web 聊天 UI | 左栏聊天面板：画师在 Web 输入"再朴素一点"等同写 inbox | 复用 B 的图廊、档案预览 |
| 5 | Web 编辑表单 | 角色档案 / prompt 字段在 Web 表单里改 → 写回 markdown | 复用 B 的 spec 渲染 |
| 6 | 跨平台支持 | Skill + Web Server 在 Windows / macOS 都过测试 | B 应已支持，C 显式验收 |
| 7 | 实时输出推送 | Skill 跑过程中往 `.runtime/jobs/*.json` 写状态 → Web SSE 推到聊天框 | B 是轮询，C 升级为 SSE |

### 4.2 画师 C 阶段的实际操作

```
画师（CC 终端）：/character-workflow 暗影刺客女
Skill：[跑一段 → 生成 spec.md → 推到 Web → turn 结束]
画师：[切到浏览器，看 Web 上的 spec 草稿]
       [Web 表单里改"年龄 22 → 24"，点保存]
Web：[写回 characters/shadow_spear_warrior.md；提示"已保存，回 CC 输入'继续'"]
画师（回 CC）：继续
Skill：[读最新 spec.md → 生成 prompt → 推到 Web → turn 结束]
画师：[Web 上看 prompt，觉得没问题，点"确认出图"]
Web：[写 .runtime/inbox/<ts>.md = "确认出图"；提示画师回 CC 输入"继续"]
画师（回 CC）：继续
Skill：[读 inbox → 调 Lovart → PNG 落地 → 推 Web]
画师：[Web 图廊看图，第 2 张矛太花]
       [聊天框输入"这把矛太花，再朴素"，点发送]
Web：[写 inbox]
画师：继续
Skill：[读 inbox → 改 prompt → 推 Web]
...
```

**回 CC 输"继续"是 C 阶段最大的 UX 摩擦点**。优化方向：
- Web 提交后自动复制"继续"到剪贴板
- Web 大字醒目提示
- V2.5 探索 CC IDE 集成 API 是否能从 Web 触发

### 4.3 显式不做（C 阶段）

| 不做 | 原因 |
|---|---|
| Web 直接触发 Claude | 需要 hack CC 的 hook 或外部 trigger，复杂且脆；回合制简单可靠 |
| Spawn 一个"代画师"的 agent 进程 | 画师 = CC 用户，没有代理人 |
| 账号 / 鉴权 / 多用户 | localhost 单人 |
| 部署到云 | V3 议题 |
| 移动端 / 平板适配 | 设备明确是 PC + Mac |
| 多 agent host（OpenClaw / Codex）的 Web Server 适配 | Skill 内核可移植，但 Web Server 这层 C 阶段只在 CC 验证；多 host 验证留 V3 |
| 自动切换模型（GPT Image 2 / Nano Banana / SD） | Lovart 后端已聚合多模型；UI 切模型逻辑放到 V3 |

### 4.4 跨平台具体要求（PC + Mac）

| 维度 | 要求 |
|---|---|
| **路径分隔符** | 全用 `path.join`，不写硬编码 `/` 或 `\` |
| **文件监听 API** | Node `chokidar` 或 Python `watchdog`，跨平台抽象 |
| **浏览器自动弹起** | `open` (mac) / `start` (win) 命令，封装在 Skill 工具里 |
| **端口冲突** | 默认 5173，被占用时自动 +1 找空端口，告诉画师 |
| **路径长度限制** | Windows 默认 260 字符限制：images/ 命名规范需要短到不踩坑 |
| **中文路径** | 全程 UTF-8，Windows 默认 GBK 的命令行下确认渲染正确 |
| **CI 测试** | GitHub Actions 双矩阵：macos-latest + windows-latest |

### 4.5 关键技术风险（C 独有）

| 风险 | 说明 | 缓释 |
|---|---|---|
| **回合衔接 UX 摩擦** | 画师每次在 Web 提交都要切回 CC 输"继续"，第 N 次会嫌烦 | (1) 剪贴板自动复制；(2) Web 醒目提示；(3) V2.5 探索 CC IDE 集成 |
| **inbox 文件竞态** | 画师快速连发两条修改，Skill 一次性读到 | 按时间戳序处理，Skill 跑前 lock 目录，跑完再 unlock |
| **画师误删 `.runtime/`** | 整个会话状态丢 | `.runtime/` 加 README 警示；周期性备份到 `.runtime-archive/`；关键状态也写一份到角色档案 |
| **Web 改 spec 时 Skill 同时写** | C 阶段 Skill 在 turn 里跑，画师不应能同时编辑；但理论可能 race | 简单乐观锁：每个 markdown 带 `version` 字段，写之前比对；冲突时报错让画师裁决 |
| **跨平台浏览器自动弹起失败** | 某些 Windows 配置 `start` 命令不工作 | fallback：打印 URL 让画师手动复制 |

    ├── jobs/
    │   └── job-001.json
    ├── inbox/                          # Web → Skill 输入队列（V2 C 起）

    └── server.pid

<image_storage_root>/                   # 画师在配置时选定的外部目录（不进 Git）

### 5.2 谁读谁写矩阵

| 文件 / 目录 | Skill 读 | Skill 写 | Web 读 | Web 写 |
|---|---|---|---|---|
| `characters/*.md` | ✅ | ✅ | ✅ | C 阶段 ✅ |
| `<image_storage_root>/**/*.png` | ❌（只调 Lovart 写）| ✅ | ✅ | ❌ |
| `memory/character-prefs.md` | ✅ | ✅ | ✅ | C 阶段 ✅ |
| `design-system/visual-style.md` | ✅ | ❌（画师手改）| ✅ | ❌ |
| `.runtime/config.json` | ✅ | 首次 ✅（初始化）| ✅ | ✅（设置面板）|
| `.runtime/jobs/*.json` | ✅ | ✅ | ✅ | ❌ |
| `.runtime/inbox/*.md` | ✅（C） | ❌ | ❌ | ✅（C） |
| `.runtime/inbox-processed/*.md` | ❌ | ✅（C，处理后移动）| ✅（V3 审计用）| ❌ |
| `.runtime/server.pid` | ✅ | ✅（启停时）| ❌ | ❌ |

**唯一写入规则**：每个文件只有一个"主人"。Web 改 spec 实际是"代画师写"，画师视角下仍是一个人在改。

### 5.3 jobs/*.json 数据契约

```json
{
  "job_id": "job-001",
  "character_id": "shadow_spear_warrior",
  "scene": "standing",
  "status": "running | done | failed",
  "started_at": "2026-05-15T14:30:00+08:00",
  "finished_at": "2026-05-15T14:30:42+08:00",
  "prompt": "青年女性，24岁，纤瘦但精瘦的体型...",
  "negative_prompt": "明亮欢快色调...",
  "references": ["design-system/references/shadow_aesthetic_01.png"],
  "output_paths": [
    "<image_storage_root>/shadow_spear_warrior/standing_20260515-1430_01.png",
    "<image_storage_root>/shadow_spear_warrior/standing_20260515-1430_02.png"
  ],
  "model": "gpt-image-2",
  "version": 1
}
```

`version` 字段为 C 阶段乐观锁服务。

### 5.4 inbox 输入队列约定（C 阶段）

文件名 = ISO 时间戳（精确到秒），Skill 按文件名升序处理。

```markdown
---
type: chat | edit_spec | edit_prompt | confirm_generate
character_id: shadow_spear_warrior
job_id: job-002              # 仅 edit_prompt / confirm 类需要
---

这把矛太花，再朴素一点
```

| type | 含义 |
|---|---|
| `chat` | 自然语言反馈，Skill 当作对话上下文 |
| `edit_spec` | 画师在 Web 表单改了 spec，body 是 diff 描述 |
| `edit_prompt` | 改某个 job 的 prompt，body 是新 prompt 全文 |
| `confirm_generate` | 纯确认信号，body 可为空 |

Skill 读完一个 inbox 文件 → 移到 `inbox-processed/`，避免重复处理。

### 5.5 同步机制总览

```
画师操作 → 写文件 → 文件监听 → 通知对方
─────────────────────────────────────────
1. 画师在 CC 终端反馈 / 确认
   → Skill 直接读上下文
   → Skill 写 jobs/*.json 或 PNG
   → Web Server 监听 .runtime/jobs/ 和 <image_storage_root>/
   → Web 前端 SSE（C）或轮询（B）刷新

2. 画师在 Web 改 spec / 提交反馈（C 阶段）
   → Web Server 写 characters/*.md 或 .runtime/inbox/*.md
   → 提示画师回 CC 输"继续"
   → 画师在 CC 输入"继续"
   → Skill 读 inbox/ → 处理 → 移到 inbox-processed/
   → Skill 写新状态 → Web 自动刷新
```

### 5.6 Git 策略

| 路径 | Git 行为 |
|---|---|
| `characters/`, `memory/`, `design-system/`, `docs/`, `skill/` | 追踪 |
| `.runtime/` | gitignore |
| `<image_storage_root>/` | gitignore（位于项目外，根本不进 Git） |

**多画师协作**：通过 Git 同步代码、角色档案、记忆。图片走画师本地选择的存储路径（可以是同一个 NAS / 同步盘 / 也可以各人独立）。每个画师有独立 `.runtime/`，互不干扰。

## 6. 图片存储路径配置

**约束**：图片不进 Git，存到画师本地可访问的任意文件夹。**不预设 NAS / 同步盘 / 团队规范**——可能是公司用户、也可能是个人用户，由画师自己决定。

### 6.1 配置文件

```json
// .runtime/config.json （每个画师本地一份，gitignore）
{
  "image_storage_root": "/Volumes/Shared/game-art/images"
}
```

路径示例（仅作参考，不限定）：

| 场景 | 示例路径 |
|---|---|
| Mac 挂载共享盘 | `/Volumes/Shared/game-art/images` |
| Windows 映射网络盘 | `Z:\game-art\images` |
| 个人 Dropbox | `~/Dropbox/game-art/images` |
| 纯本地用户 | `~/Documents/game-art/images` |

### 6.2 配置入口

| 阶段 | 入口 |
|---|---|
| **B 阶段** | Web UI 第一次启动弹一个简单设置页：画师选 / 粘贴目录，Web 写入 `.runtime/config.json` |
| **C 阶段** | Web UI 设置面板，可随时改路径（改完旧路径里的图不动，新出的图走新路径） |

### 6.3 读取与失败处理

- Skill 每次出图前读 `.runtime/config.json` 取 `image_storage_root`
- 没配置 → 报错给画师"先打开 Web UI 设置图片目录"
- 路径不可写 → 报错给画师，让画师确认共享盘 / 网盘是否挂载在线
- Skill 写 PNG 到 `<image_storage_root>/<character_id>/<filename>.png`
- Web Server 启动时读 `image_storage_root`，挂载为 HTTP 静态目录（如 `/static/images/`）
- 路径不可访问 → Web 显示"图片目录不可用"，引导画师重新配置

## 9. 底线坚持（产品哲学锚）

无论后续怎么演进，以下原则不动：

1. **文件系统是唯一 source of truth**。任何 UI 都只是文件的视图。
2. **Skill 内核纯 markdown + tool calls**，不绑死任何 agent host。
3. **画师写动作的最终归宿是文件**，不是数据库 / 不是云 / 不是内存。
4. **画师本地有完整权力**：随时用 PS / Finder / VS Code / 记事本绕过 UI 直接改。
5. **零部署、零账号、零云**（V1 + V2 全周期）。
