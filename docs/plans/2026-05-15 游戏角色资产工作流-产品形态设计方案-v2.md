## 0. 一句话决定

**Skill 主交互 + 本地 Web UI 双向 + 剪贴板桥接，单阶段 2 周一步到位。**

- Skill 跑在画师自己的 Claude Code 里（用画师自己的 Claude 账号）
- 本地 Web UI 是 Skill 启动的伴生窗口，localhost，无服务器、无云、无账号
- 画师**主体在 Web 工作**：看图、编辑 prompt、改角色档案、提反馈
- 画师"触发下一轮"用 **1.5 次操作**：在 Web 点保存后，回 CC 按 `Cmd+V` + `Enter`（"继续"已自动复制到剪贴板）
- 文件系统是唯一 source of truth；图片不进 Git
- **取消 v1.0 的两阶段路径**（B 只读看图 → C Web 主交互）

## 2. 前提修订记录（office-hours 2026-05-15 会话）

v1.0 隐含的三个前提，会话中被推到台面验证。结果：

| v1.0 前提 | 验证后状态 | 修订方向 |
|---|---|---|
| **画师不愿在 CC 终端打字、心智门槛高** | ❌ 不成立 | 画师当前**已经在跟 LLM 对话**（喂资料、改 prompt、反复出图）。"不愿打字"是创业者投影，不是事实 |
| **真痛点是"画师对终端不熟"** | ❌ 不成立 | 真痛点是**"重复喂上下文"**——每接一个新角色都要重新喂项目资料/已有形象/风格基线给 LLM。Skill 直接解药 |
| **C 阶段必须"Web 主交互"为画师不愿打字买保险** | ⚠️ 部分修订 | 画师**确实必须图形界面**（终端看不了图、编辑长 prompt 反人类），但"图形界面"≠"Web 退到后端"。B+ 在保留 Skill 主导的同时让画师全程在 Web |

**保留不动的原则**（v1.0 §9 哲学锚仍然有效）：

1. 文件系统是唯一 source of truth
2. Skill 内核纯 markdown + tool calls，不绑死任何 agent host
3. 画师写动作的最终归宿是文件
4. 画师本地有完整权力（PS / Finder / VS Code 绕过 UI 直改）
5. 零部署、零账号、零云

| 服务器 / 账号 | 无 | 无 | **无** | 无 | 无 |
| 哲学锚（不绑死 host）| ✅ | ✅ | **✅** | ✅ | ❌ |
| 未来 SaaS 演化 | 要重写 UI | 要重写主交互 | **天然支持**（前后端分离的 localhost 版） | 天然支持 | 桌面 App 推倒 |

**为什么选 B+**：

1. **A、D 仍按 v1.0 理由淘汰**（A 看不了图、D 绑死 host）
2. **B 路径过于保守**：只读看图无法验证"画师能不能在 Web 完整工作"这个 v2.0 核心问题
3. **C 路径多余**：v1.0 把 C 当成"Web 主交互的最终形态"，但 C 设计了一套 inbox 队列 + "回 CC 输继续" 的回合制摩擦——这些是为了**强行让 Web 反向触发 Skill** 而引入的复杂度。B+ 用剪贴板桥接 1.5 次操作绕开
4. **B+ 同时拿到了 v1.0 的两个目标**：Web 完整 GUI（"以人为本"）+ Skill 内核可移植（架构哲学锚）
5. **B+ 工期最短**（2 周 vs A 路径的 3-4 周），且没有"B 阶段画师感受不到完整产品"的验证盲区

## 4. B+ 阶段范围（取代 v1.0 §3 + §4）

> **关于技术栈**：本设计仍是 stack-agnostic。Web Server 用 Node 还是 Python、前端用 React 还是 Vue——留给 writing-plans 阶段定盘。

```
│  │                  │  │  - 编辑 prompt   │  │

│  │  画师 Cmd+V +    │  │  - 反馈输入框    │  │
│  │  Enter 触发回合  │  │                  │  │
│  └──────────────────┘  └──────────────────┘  │
│        │     ↑              ↑     │          │
│        ▼     │              │     ▼          │

│  └──────────────────────────────────────┘   │

【回合制】Web 改 → 文件落盘 + 剪贴板复制"继续"
```

**关键约束**：

- 文件系统是唯一数据源
- 画师**主体感受是在 Web 工作**，CC 终端只是"按个键触发下一轮"
- Skill 内核**零修改**，仍以"读文件、调工具、写文件"工作
- Web Server 不调任何 Claude API、不持有任何 token

### 4.2.A 交付物 4 详细设计规格（/plan-design-review v2.3 补充）

> 本节由 /plan-design-review 审查后补充，消除 writing-plans 阶段的 UI 实现歧义。

#### 三栏布局规格

| 模式 | 左栏 | 中栏 | 右栏 |
|------|------|------|------|
| 默认（规格表单）| 20% | 50% | 30% |
| 图片详情模式 | 20% | 30%（缩略图压缩为 2 列）| 50%（大图 + 元信息）|

- **分辨率基准**：1440px 宽；最小支持 1280px（不支持移动端，localhost 桌面工具）
- **色彩体系**：深色主题（背景近 `#0F0F0F`）；主操作色蓝（`#3B82F6` 或同色系）；状态色：生成完 = 绿，生成中 = 黄（脉冲动效），出图失败 = 红
- **字号层级**：栏标题 15px/semibold → 字段标签 13px/medium → 字段值 14px/regular → 时间戳/次要 12px/gray

#### 图廊交互模式（D1 决策：右侧详情面板）

- 默认：中栏缩略图格子 4 列，右栏为规格表单
- **点击缩略图** → 中栏压缩为 2 列 + 右栏切换到"图片详情"模式
  - 右栏上半（约 60%）：大图展示
  - 右栏下半（约 40%）：可编辑元信息字段（prompt / model / params / seed / submitted_at），每字段右侧有复制按钮
  - 复制 prompt 字段 = 触发剪贴板写入"继续 + 改后的 prompt"，画师切 CC 即可触发重出图
  - 右栏顶部有 **← 返回** 按钮，点击回到规格表单模式
  - 快捷键：**Esc** 关闭详情模式（等同于点← 返回）
  - 焦点管理：打开详情时焦点移入详情面板；关闭时焦点回到触发的缩略图

> **消歧说明**：§4.2 交付物 4 原文"中 = 图廊缩略图 + 大图"的"大图"指右侧详情面板内的大图，**非**中栏展开、**非** Lightbox 全屏覆盖。writing-plans 开发者直接按此执行。

#### "任务进度"实现说明

§4.2 交付物 4 中"左 = 任务进度 + 角色列表"的**任务进度以角色列表项的状态徽章实现**，不另设独立区块：

| 徽章状态 | 颜色 | 说明 |
|----------|------|------|
| 生成中 | 黄色 + 脉冲动效 | Skill 正在出图 |
| 生成完 | 绿色 | 本轮出图完成 |
| 出图失败 | 红色 | API 错误，可在图廊错误卡点重试 |
| （无徽章）| — | 角色档案已建，尚未触发出图 |

#### 状态覆盖（loading / empty / error / conflict）

| 组件 | 状态 | 表现 |
|------|------|------|
| 左栏 | Empty（0 个角色）| 隐藏列表，居中显示"+ 新建第一个角色"大按钮 + 一句简介 |
| 左栏 | 角色生成中 | 该角色列表项显示黄色脉冲徽章"生成中" |
| 图廊 | Empty（新角色，无图）| 居中图标 + "还没有出图，保存档案后触发第一轮" |
| 图廊 | Loading（生成进行中）| 4 个骨架占位卡（shimmer 动效），每卡标签区显示"生成中…" |
| 图廊 | Error（出图失败）| 错误卡片：感叹号图标 + "出图失败 [重试]" 链接 |
| 图廊 | SSE 新图到达 | 图廊顶部横幅"新图已到 [刷新展示]"，**不自动刷新**（防打断画师当前查看）|
| 规格表单 | Dirty（有未保存改动）| 保存按钮区域显示"·"或"未保存"小字标记 |
| 规格表单 | Auto-save（5s 后静默落盘）| 不显示 toast，无 UI 反馈 |
| 通知条 | 剪贴板失败（降级）| 琥珀色横幅 + "[手动复制'继续']" 可点按钮 |
| 通知条 | 冲突检测（§5.4）| 顶部小字"文件已变更 [刷新]"，不阻断画师编辑 |


**核心 UX 节奏**：
- **画师 90% 时间在 Web**（看图、编 prompt、改 spec、写反馈）
- **画师每轮触发只需 Cmd+V + Enter**（剪贴板已就绪，1.5 次按键操作）
- **Skill 不感知"是 Web 触发还是终端触发"**——它每次 turn 起始都重新读文件，所以从它视角看就是文件变了

### 4.4 剪贴板桥接机制（B+ 核心创新点）

**问题**：v1.0 C 阶段需要画师"切到 CC 窗口、用键盘打字'继续'"——这是最大的 UX 摩擦。

**B+ 解法**：浏览器 Clipboard API + 一条用户教育信息。

| 步骤 | 实现 | 说明 |
|---|---|---|
| Web 提交后写文件 | `POST /xxx` 落盘 | 仍是文件系统作为 source of truth |
| 自动复制 "继续" | `navigator.clipboard.writeText('继续')` | 浏览器原生 API，HTTPS / localhost 可用 |
| Toast 提示 | 顶部固定条："已保存。切到 CC 按 `Cmd+V` `Enter`" | 强提示让画师形成肌肉记忆 |
| 画师动作 | 切窗口 + 粘贴 + 回车 | 1.5 次按键（粘贴 + 回车），切窗口在 Mac 是 Cmd+Tab |

**降级方案**：

| 失败场景 | 降级 |
|---|---|
| Clipboard API 失败（浏览器禁权限）| toast 内容改为可点击的"复制'继续'"按钮 |
| 画师老忘记切窗口 | viewer-server 启动时打印"提示：Web 改完后切回这里 Cmd+V Enter"到 CC 控制台，每次 Skill turn 结束也提示一次 |
| 画师就是不愿切 | V2 议题：探索 CC IDE 集成 API 是否能从 Web 触发 turn |

**为什么不做"Web 直接触发 Skill"**：

- CC 没有"文件变化时触发 turn"的 hook（只有 `PreToolUse` / `Stop` 等基于 turn 生命周期的 hook）
- 自己起 daemon 轮询文件 → 调 Claude Agent SDK：要画师配 API key、装 daemon、不再用画师自己的 Claude 账号——违反"零部署、零账号"原则
- 切 OpenClaw / 其他 host：今天画师装 CC 已经是事实，再换 host 等于推倒重来
- **结论**：剪贴板桥接是当下成本最低、约束最少的解。1.5 次按键的画师摩擦，远小于其他方案的开发或运维代价

### 4.5 显式不做（B+ 阶段）

| 不做 | 原因 |
|---|---|
| inbox 队列 + lock + 时间戳排序 | B+ 的 Web 写动作直接落盘到对应文件（`characters/*.md`、`jobs/*.json`、`draft/*.md`），不需要排队 |
| Web 主动反推 Skill | 剪贴板 + Cmd+V Enter 已经够低摩擦 |
| 多用户 / 账号 / 鉴权 | localhost 单画师 |
| 图片精细对比（slider）| V2 议题 |
| 历史版本回溯 UI | Git 已经够 |
| WebSocket（双向持久连接）| SSE 单向推送已足够（服务端→客户端变化通知）；WebSocket 引入额外握手和状态管理复杂度，不值得 |
| Web 直接触发 Claude API | 画师用自己 Claude 账号 + Skill 在 CC 跑，Web 不持任何 token |
| 自动切换出图模型 | Lovart 已聚合多模型；UI 切模型 V3 |

### 4.6 验收标准（v2.1 回填）

B+ 上线后 4 周内必须全部达成。任何一项失败 → 触发 v2.x 修订。

**M1 · 画师独立完成度（硬指标）**
画师在上线 2 周内独立完成 ≥ 3 个完整角色（从 spec 编写到 4 张终选图通过画师自评 ≥ 7/10），全程**不需要项目负责人介入解释概念或排查问题**。介入 1-2 次（教学性质）可接受；介入 3+ 次 = 失败。

**M2 · 触发回合摩擦（硬指标）**
"Web 保存 → CC 触发下一轮"的 90 分位耗时 ≤ 5 秒，剪贴板桥接 7 天滑动窗口成功率 ≥ 95%。失败时降级方案（toast 内"复制'继续'"按钮）必须 100% 可点。

**M2 测量机制**（v2.2 补充）：Web 每次尝试写剪贴板后，立即 `POST /clipboard-attempt` 上报结果（`{ts, success: true/false, reason}`）；server.log 追加该记录。上线 1 周后统计 `success` 字段得出成功率。

**M3 · 可观测性可用性（硬指标）**
画师报告任何"Web 改完但 Skill 没反应"问题时，能在 30 分钟内仅凭画师电脑上的 `.runtime/jobs/*.json` + Web 元信息面板截图复现并定位根因。无法定位 = 失败。

**M4 · 画师主观评分曲线（学习曲线指标）**
上线第 1 周末 + 第 4 周末各做一次 4 题 1-10 分自评：
1. UI 顺手度（看图、编 prompt、改档案的总体感受）
2. 触发回合的认知负担（Cmd+V Enter 是肌肉记忆 还是 心智负担）
3. 看图/对比图体验（vs Finder + Preview）
4. 比"直接跟 LLM 聊天"是否更高效

**通过条件**：第 4 周综合分 ≥ 7 **且** 高于第 1 周综合分（学习曲线收敛而非放弃）。第 4 周低于第 1 周 = 触发设计反思。

**M3 实现说明**：见 §4.2 交付物 9（图片元信息面板）。每张图自带的 json + Web 面板代替传统日志，画师能直接截图发问题。

## 5. 文件模型修订（取代 v1.0 §5）

### 5.1 项目目录结构

```
game-ui-ai-workflow/
├── characters/                     # 角色档案（Git 追踪）
├── design-system/                  # 风格基线（Git 追踪）
├── memory/                         # 画师偏好（Git 追踪）
├── docs/                           # 文档（Git 追踪）
├── skill/                          # Skill 内核 + viewer-server（Git 追踪）
└── .runtime/                       # 运行时（gitignore）
    ├── config.json                 # 画师本地配置
    ├── jobs/                       # 出图任务状态
    │   └── job-001.json
    ├── draft/                      # 画师反馈草稿（Web 写、Skill 读完即移走）
    │   └── 20260515-143012.md
    ├── draft-processed/            # 已读 draft 归档
    └── server.pid

<image_storage_root>/               # 画师本地路径（不进 Git）
```

**相对 v1.0 的变化**：

- `inbox/` → **`draft/`**（语义更准：画师在 Web 上写的"草稿反馈"，Skill 下次 turn 起始读取）
- 取消复杂的 inbox lock / 时间戳排序：每个 draft 文件独立、Skill 一次性全读、读完移到 `draft-processed/`

### 5.2 谁读谁写矩阵

| 文件 / 目录 | Skill 读 | Skill 写 | Web 读 | Web 写 |
|---|---|---|---|---|
| `characters/*.md` | ✅ | ✅ | ✅ | **✅** |
| `<image_storage_root>/**/*.png` | ❌ | ✅（调 Lovart 落地）| ✅ | ❌ |
| `memory/character-prefs.md` | ✅ | ✅ | ✅ | **✅** |
| `design-system/visual-style.md` | ✅ | ❌（画师手改）| ✅ | ❌ |
| `.runtime/config.json` | ✅ | 首次 ✅ | ✅ | ✅ |
| `.runtime/jobs/*.json` | ✅ | ✅ | ✅ | **✅（改 prompt）** |
| `.runtime/draft/*.md` | ✅ | ❌ | ❌ | **✅** |
| `.runtime/draft-processed/*.md` | ❌ | ✅（处理后移动）| V3 审计 | ❌ |

### 5.3 Skill 主循环锚点

每次 Skill turn 起始**必做**：

1. 读 `.runtime/draft/*.md`，按文件名升序合并到当前上下文
2. 把读过的 draft 移到 `.runtime/draft-processed/`
3. 检查 `characters/<active>.md` 时间戳是否新于上次读取——是则重读

这一个三步骤是"Web 写 → Skill 读"的全部桥接逻辑。**没有 inbox 队列、没有 lock、没有 SSE**。

### 5.4 Skill ↔ Web 并发写约定（v2.1 新增）

文件系统始终以**落盘版本**为准（"本地优先"）。Web 表单编辑期间 Skill 写入同一文件时不强制中断画师，采用非破坏式同步策略。

**Web 端机制**：

| 概念 | 行为 |
|---|---|
| 表单状态 | "未保存的工作副本"，**不等于**落盘文件 |
| 自动保存 | 表单变更后 5s 静默落盘（不触发剪贴板）|
| 手动保存 | "保存"按钮立即落盘 + 自动复制"继续"到剪贴板 + toast 提示 |
| 检测落盘变更 | 每 2s 轮询文件 mtime/hash；发现"文件内容比表单上次同步时新" → 顶部**小字提示"内容已变更，[刷新]"**，**不自动覆盖画师未保存草稿** |

**Skill 端机制**：
- Skill turn 内自由读写 `characters/*.md`、`.runtime/jobs/*.json`
- Skill 不持锁，假设画师配合"Web 表单看到刷新提示时主动决策"

**冲突解决**：
- Skill 写 → Web 检测到 → 提示画师 → 画师选择"刷新"（丢草稿用 Skill 版本）或"保存"（用画师版本覆盖）
- 罕见竞态（画师点保存的瞬间 Skill 也在写）→ **last writer wins**；Web 下次 2s 轮询会发现内容变化再次提示
- **不引入文件锁**。代价：极小概率画师看到的不是最新落盘状态，由提示机制兜底

**为什么不锁**：v1.0 的 inbox lock 在 v2.0 已经被否定。锁带来的复杂度（残锁清理、跨进程语义、画师误操作）远大于"罕见竞态被提示兜底"的代价。

## 6. 三个澄清记录（office-hours 决策依据）

### 6.1 "全程 Web 操作 = 等于做了个网站产品 = 找开源改？"

❌ 类别错误。

| 你产品的真正核心 | 市面上有现成的吗 |
|---|---|
| Web 聊天 + 出图渲染 | ✅ ComfyUI / Open WebUI / Lobe Chat 一抓一把 |
| 角色档案规范、画师偏好长期沉淀、Skill 可复用 | ❌ 没有，是本项目独有的护城河 |

开源 chat front-end 是 5w+ 行的复杂项目，把"角色档案规范 + 长期沉淀"塞进去 = 拆它的内部数据模型重写。**自己写 localhost web app 的真实成本：Server 100-200 行 + 前端 200-300 行**。比改开源便宜得多，且不背上游版本包袱。

### 6.2 "Skill 对话回到终端，从网页怎么传回？"

剪贴板桥接（见 §4.4）。这是当下成本最低、约束最少的解。其他三条路（CC file hook / OpenClaw / CC IDE API）都因为不可行或违反"零部署、零账号"原则被淘汰。

### 6.3 "Skill 数据本地 / 网站数据线上，怎么抉择？"

不存在这个抉择。**B+ 里的 Web 是 localhost**（画师本机的 5173 端口），数据全在画师本地文件系统，不出本机。"零部署、零账号、零云"哲学锚 100% 保留。"线上"是 V3 SaaS 议题，B+ 不碰。
