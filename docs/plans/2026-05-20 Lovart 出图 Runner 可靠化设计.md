# Design: Lovart 出图 Runner 可靠化

Generated by /office-hours on 2026-05-20

Repo: game-ui-ai-workflow
Status: DRAFT
Mode: Builder

## Problem Statement

这次 `holy-spirit-priestess` 美宣能跑通，不是因为系统可靠，而是因为人手把长期记忆里的补丁串起来了：

- `lovart_caller.py` 还在找 `~/.claude/skills/lovart-api/lovart`，但实际稳定入口是 wrapper5。
- wrapper5 在 `/tmp`，不是项目资产，重启或清理后会消失。
- job 有 `source_image`，但 Lovart 调用和 Web 展示读的是 `params.reference_images`。
- 上传、下载、代理清理、artifact 筛选、状态更新都靠终端人工拼。

这是一个状态机和执行器缺失问题，不是 26 个独立 bug。

## What Makes This Worth Fixing

角色资产工作流的用户不是在调 API。他们只想说“出图”，然后看到正确图片落到正确目录，Web 和终端状态一致，下一轮还能追溯这张图用了什么参考图、哪个 prompt、哪个 Lovart artifact。

当前系统最危险的点是“看起来已完成”。`.runtime/jobs/job-202605200716545936cf44.json` 已经是 `done`，也有 `promo/v1.png`，但 `params.reference_images` 仍是 `[]`。以后复盘会以为没用参考图。这个错比直接失败更坏。

## Evidence From Code

- `skill/character_workflow/lib/lovart_caller.py:21` 默认入口硬编码为 `~/.claude/skills/lovart-api/lovart`。
- `skill/character_workflow/__main__.py:51-56` submit 默认把 `reference_images` 写成空数组。
- `skill/character_workflow/__main__.py:67` 只把 `source_image` 写到 job 顶层。
- `skill/character_workflow/lib/jobs.py:70-82` `update_job_status(..., error=None)` 不会清空旧 error。
- `web/src/components/CharacterGallery.tsx:380-390` PendingConfirmBadge 只显示 “N 个 job 等终端确认”，不展示参考图、尺寸、prompt 摘要。
- `characters/holy-spirit-priestess/portrait/lovart_94edf9541ee6.png` 是 0 字节文件，证明“latest by mtime”会污染资产选择。
- `.runtime/jobs/job-2026051807362138b5c9fb.json` 是 `status=done` 但仍残留旧 `error`，现象已复现。

## Premises

1. Lovart 可靠性必须固化到项目代码或项目 skill，不能靠 `~/.claude/MEMORY.md` 和 `/tmp/lovart_wrapper5.py`。同意。
2. 修复中心应该是一个统一 runner：读取 job，确认，上传参考图，调用 Lovart，筛选 artifact，落盘命名，更新 job。不是让每个 Skill 自己拼命令。 同意。
3. `source_image` 和 `params.reference_images` 不能继续表达同一概念。需要明确：本地源图、Lovart 远端附件 URL、Web 展示参考图各自是谁。 同意。
4. Web 端暂时保持“查看 + 复制命令”，不恢复副作用确认按钮。决策面仍在终端，避免误触发外部出图。 同意。

## Prioritization

### Must Fix Now

这些不修，下一次出图仍会随机失败或写脏状态。

1. **Lovart transport 固化**
   - 不要把 `DEFAULT_LOVART_CLI` 改成 `/tmp/lovart_wrapper5.py`。
   - 把稳定 wrapper 固化到项目或上游 `lovart-api` skill。
   - 运行时显式禁用污染代理：shell env 清空只是兜底，HTTP session 应该 `trust_env=False`。

2. **Unified runner**
   - 新增类似 `python -m skill.character_workflow run-job <job_id>`。
   - runner 负责 `PENDING_CONFIRM -> PENDING -> Lovart -> DONE/FAILED`。
   - 用户只说“出图”时，runner 能找到当前 active character 最近一个 `pending_confirm` job。

3. **Reference image contract**
   - `source_image` 是本地原始参考图。
   - `params.reference_images` 用于 Web 展示和本地调用输入，至少应自动包含 `source_image`。
   - Lovart 上传后返回的远端 URL 应写入新字段，例如 `params.lovart_attachments`，不要覆盖本地源图。

4. **Status update can clear error**
   - `update_job_status` 需要一个显式 sentinel，区分“不改 error”和“清空 error”。
   - 成功态必须清空旧 error，否则 `done + error` 会继续污染 Web 和复盘。

5. **Artifact boundary and valid image filter**
   - 优先每个 job 新建 Lovart thread，避免历史 artifacts 混入。
   - 如果 Lovart 仍返回多张历史图，先下载到 temp，再按本次 thread/message/artifact metadata 筛。
   - 所有候选图必须过 `latest valid image` 校验：非 0 字节、能被图片库打开、尺寸符合 kind 预期。

### Should Fix Next

这些会影响可维护性和复盘，但不是下一次出图的第一阻塞。

6. 自动分配 `vN.png` 和 `vN.md` sidecar。
7. `params.size` 改语义：`requested_size` 和 `actual_size` 分开，Lovart 不支持硬 `--size` 时 UI 不要暗示它强约束模型。
8. 失败下载自动 fallback 到 `curl -sS` 或 requests streaming。
9. 旧 0 字节 Lovart 文件由 runner 忽略，另加 `doctor`/cleanup 建议，不在普通出图流程里删除历史文件。
10. DONE 后生成候选 lesson，不要只问“要不要沉淀”。

### Can Defer

这些是体验优化，不该塞进第一轮可靠化。

11. Web 端恢复确认按钮。
12. 冷启动 message 槽位自动解析更多自然语言。
13. `.runtime/jobs` 是否进 git。运行时不进 git 是对的，但需要 `docs/api-contract.md` 明确它是 local source of truth，不是版本化 source of truth。

## Bad Fixes To Avoid

1. **把路径硬改成 `/tmp/lovart_wrapper5.py`**
   这是把已知事故写进代码。`/tmp` 不是依赖管理。

2. **只在文档里补“记得清空 proxy”**
   这还是靠人脑。runner 应该默认构造干净 env，transport 自己不要读系统 proxy。

3. **把 `source_image` 复制到 prompt 文本就算引用**
   模型不一定看得到图。参考图必须进入 Lovart attachment/reference 参数，并写入 job。

4. **看到 `final_status=timeout` 就标 failed**
   如果已有有效 artifact，用户结果是成功。应该 `DONE + warning`，不是失败。

5. **按 mtime 选“最新图”**
   0 字节文件已经证明这个方案不成立。

6. **先下载所有 artifacts 到目标目录再筛**
   这会把旧立绘拉进 `promo/`。应该 temp 下载，筛完再 move/rename。

7. **把所有 asset kind 做成一个大参数化 pipeline**
   现在只需要共享 runner 和 artifact 处理。portrait/promo/turnaround 的 prompt 对话继续分 Skill，避免一个超级 if-else。

8. **确认前写 spec 正式美宣记录**
   job 没 DONE 前只写 `.runtime/jobs` 草稿态。正式记录应在 DONE 后落 sidecar 或 spec history。

## Approaches Considered

### Approach A: Minimal Patch

Summary: 更新 `lovart_caller.py` 使用稳定 wrapper 路径，submit 时把 `source_image` 填进 `reference_images`，修 `update_job_status` 清 error。

Effort: S
Risk: Medium

Pros:
- 文件少，能最快解除 P0。
- 测试增量小。

Cons:
- 仍没有 runner，确认后执行靠人拼。
- artifact 历史污染和下载 fallback 仍会复发。
- 继续把“流程”散落在 Skill 文档和终端习惯里。

Reuses:
- 现有 `lovart_caller.py`、`jobs.py`、`submit` CLI。

Completeness: 5/10

### Approach B: Job Runner Spine

Summary: 新增 runner 作为出图唯一执行入口。Skill 只负责生成 `PENDING_CONFIRM` job，runner 负责确认、上传、Lovart 调用、artifact 筛选、命名、状态更新。

Effort: M
Risk: Medium

Pros:
- 一次解决 P0 和大多数 P1。
- 把人脑流程变成可测试代码。
- Web、终端、job JSON 读同一个协议。

Cons:
- 需要补一组端到端测试。
- 需要小幅调整 Skill 文档和 Web badge 文案。

Reuses:
- `jobs.write_job/read_job/update_job_status`
- `job_output_dir`
- `lovart_caller.submit_and_wait`
- 现有 `submit` CLI 和 kind schema

Completeness: 9/10

### Approach C: Full Lovart Skill Fork/Upstream Fix

Summary: 直接修 `lovart-api` skill，让它原生使用 requests、禁 proxy、上传下载都稳定，再让本项目只调用官方入口。

Effort: L
Risk: Medium

Pros:
- 根因最干净，其他项目也受益。
- 项目内少维护 Lovart 协议细节。

Cons:
- 超出本项目边界。
- 上游 skill 更新和同步 Codex/Claude skill 有额外发布成本。
- 本项目仍需要 runner 管 job 状态和 artifact 边界。

Reuses:
- 外部 `lovart-api` skill。

Completeness: 8/10

## Recommendation

选 Approach B。A 是止血，但会继续让 agent 手拼执行链。C 值得做，但它只修 transport，不修 job 状态机。

Job Runner Spine 是这次的湖，不是海。模型执行量大约 45-75 分钟，主要花在测试和协议同步，不需要人类账户操作。人类只需要确认一个产品选择：Web 端是否继续保持无副作用。

## Concrete Design

### New CLI

```bash
uv run python -m skill.character_workflow run-job <job_id>
uv run python -m skill.character_workflow run-latest --kind promo --character holy-spirit-priestess
```

`run-latest` 找最近一个 `pending_confirm` job。确认动作由终端用户发“出图”触发，Skill 调 CLI，不再手动拼 Python。

### Runner Responsibilities

1. 读 job。
2. 校验 `status == pending_confirm`。
3. 把 `source_image` 归一到 `params.reference_images`。
4. 上传 reference images，记录 `params.lovart_attachments`。
5. 标 `pending`，并清空旧 error。
6. 调 Lovart transport。
7. 下载 artifacts 到 temp。
8. 按本次 job 边界筛选目标图。
9. 校验有效图片和尺寸。
10. 分配 `vN.png`，写入目标目录。
11. 写 `vN.md` sidecar。
12. `done` 时写 `output_paths`、`actual_size`、warnings，并清空 error。

### Job Metadata

最小兼容写法，保持 `JobParams.extra="allow"`：

```json
{
  "params": {
    "requested_size": "2048x1152",
    "actual_size": "2048x1152",
    "reference_images": ["/abs/local/source.png"],
    "lovart_attachments": ["https://..."],
    "lovart_thread_id": "...",
    "lovart_final_status": "timeout",
    "warnings": ["final_status timeout but 1 valid artifact selected"]
  }
}
```

### Asset Sidecar

每个正式产物旁边写：

```markdown
# v1

- kind: promo
- job_id: job-...
- created_at: 2026-05-20T...
- source_image: characters/.../portrait/v1.png
- requested_size: 2048x1152
- actual_size: 2048x1152
- style_tag: 宝可梦杉森建图鉴风
```

这比把所有历史塞进 `spec.md` 稳。spec 只保存角色真相，产物 sidecar 保存生成记录。

## Success Criteria

- 非交互测试覆盖：runner 从 `pending_confirm` 到 `done`，自动传 source image，清空旧 error。
- Lovart transport 测试覆盖：默认命令不依赖 `/tmp`，env 清空 proxy。
- artifact 测试覆盖：返回旧 artifact + 新 artifact 时只落新图。
- asset 测试覆盖：0 字节文件不会被选为 latest valid image。
- job JSON 验证：promo DONE 后 `reference_images` 非空，`output_paths` 只包含 `promo/vN.png`。
- Web 验证：Pending badge 能显示参考图存在，不再出现“参考图：无”但实际用了参考图。

## What I Noticed

- 这份 bug list 的质量很高。不是“哪里坏了”的流水账，而是抓到了协议断层：job、Web、终端、Lovart 各读各的字段。
- 你已经做了正确的产品判断：Web 不一定要放副作用按钮。先把终端 runner 做硬，比做一个漂亮但会误触发的确认按钮更值。
- 真正要避免的是“修 26 个点”。那会让系统更碎。先建 runner 脊柱，再把这些 bug 挂回同一个执行入口。
