# 角色资产 Skill 套件扩展

> 日期：2026-05-19
> 状态：DRAFT — 待用户拍板路径 A/B/C 后开始落地
> 当前实现：`skill/character_workflow/` 完成"角色设定 + 立绘"链路 80%

## 1. 用户原始设想

三个 Skill，共享"项目背景资料 + 历代经验"，各自有专属上下文和专家人设：

```
Skill #1 角色设定
  需求输入 → (项目世界观 + 精灵设定档案 + 项目资料 + 历代经验) → 角色档案专家人设
         → 角色设定档案 + 出图 Prompt → Lovart 出图

Skill #2 角色美宣图
  已有角色形象 → (精灵设定档案 + 历代美宣经验 + 项目资料) → 美宣 Prompt 专家人设
              → 美宣 Prompt → Lovart 出图

Skill #3 角色三视图
  已有角色形象 → (角色形象本身) → 三视图 Prompt 专家人设
              → 三视图 Prompt → Lovart 出图
```

未来扩展：卡图 / 动作 / 3D 模型 / 宣传视频。

## 3. 前提挑战

| # | 前提 | 结论 |
|---|---|---|
| 1 | 真的要拆三个 Skill 吗？做成 `/character-asset <type>` 参数化更简洁 | **保持分开 + 未来加"总 Skill"按需调度子 Skill**（见 §10）。专家人设差异大、对话引导差异大，参数化反而要写一堆 `if type == ...`；子 Skill 先各自完善，后续再做调度层。 |
| 2 | 当前 `character-workflow` 改名为 `character-spec`？ | **暂不改**，保留为"角色设定 + 立绘"的合一入口。Skill #1 = 现有 character-workflow + 加载世界观与历代经验。 |
| 3 | 用户上传图怎么落盘？ | **临时区 → 归档**。`.runtime/uploads/<temp_id>.png` 上传时落盘，Skill 用完挪到 `characters/<id>/source/`。 |
| 4 | 一次 Lovart 调用能出多视图（三视图），还是要拼合多次？ | **用户确认 Lovart 一次能出三视图横幅图**。Lovart prompt 段里写"三视图：正面/侧面/背面"+ 横幅比例（建议 1536×1024）。 |
| 6 | 每次出图出几张？ | **默认每个 Skill 出 1 张**（用户明示）。用户说"多出几张/出 4 张对比"再改 `n`，否则保持 `n=1`。注意：当前 `character-workflow` SKILL.md 里"一次 4 张做对比"的说法需要在重构时改成 `n=1` 默认。 |
| 5 | Web UI 要不要"一键触发 Skill"按钮？还是只能在 CC 里 `/character-promo <id>` 触发？ | **先只支持 CC 触发**。Web UI 上的按钮显示一段可复制命令字符串。后续再加 draft 派发机制。 |

### 4.3 Job 数据模型扩展

`.runtime/jobs/<job_id>.json` 增加字段：

```python
class JobKind(str, Enum):
    PORTRAIT = "portrait"      # 立绘（Skill #1 产物）
    PROMO = "promo"            # 美宣图（Skill #2 产物）
    TURNAROUND = "turnaround"  # 三视图（Skill #3 产物）

class Job(BaseModel):
    # ... 现有字段
    kind: JobKind = JobKind.PORTRAIT   # 旧 job 默认 PORTRAIT
    source_image: str | None = None    # promo/turnaround 用，绝对路径
```

`output_paths` 写盘目录按 `kind` 分发：
- PORTRAIT → `characters/<id>/portrait/`
- PROMO → `characters/<id>/promo/`
- TURNAROUND → `characters/<id>/turnaround/`

### 4.5 三个 Skill 的最终形态

**三 Skill 共用默认值**：
- `n = 1`（默认只出 1 张；用户明示"多出几张"才改）
- 出图前必经 `PENDING_CONFIRM` 确认门，确认后才调 Lovart
- 终端用 `![v1](绝对路径)` 把出图渲染出来
- turn 收尾后追加经验到对应 `references/lessons/<kind>.md`（详见 §4.7）

---

**Skill #1 `/character-workflow`**（重构后保留现名）
- 入口：`/character-workflow <名>` 或用户说"做个角色"
- 输入：用户对话需求 + 可选参考图
- 流程：`turn-start` → 加载 worldview/lessons → 角色档案专家人设 → 对话补全 spec → 写 `characters/<id>/spec.md` → 渲染立绘 prompt → 确认 → Lovart → 写 `portrait/*.png`
- 新增引用：`references/personas/spec-expert.md`、`references/lessons/portrait.md`

**Skill #2 `/character-promo`**（新建）
- 入口：`/character-promo <id>` 或 `/character-promo --upload <path>`
- 输入：已有角色 id 或上传图路径
- 流程：加载 worldview + 该角色 spec + promo lessons → 美宣 Prompt 专家人设引导（场景/情绪/构图/色调/张力）→ 渲染美宣 prompt → 确认 → Lovart → 写 `promo/*.png`
- 新增文件：
  - `skill/character_promo/SKILL.md`
  - `skill/character_promo/references/personas/promo-expert.md`
  - `skill/character_promo/references/prompt-promo-zh.md`（美宣 prompt 模板）
- 复用：`skill/character_workflow/lib/*`（context_loader / prompt_builder / jobs / lovart_caller）

**Skill #3 `/character-turnaround`**（新建）
- 入口：`/character-turnaround <id>` 或 `/character-turnaround --upload <path>`
- 输入：已有角色 id 或上传图路径
- 流程：加载角色 spec（仅外观要点）→ 三视图 Prompt 专家人设引导（视图组合 / 表情包 / 比例尺）→ 渲染三视图 prompt → 确认 → Lovart → 写 `turnaround/*.png`
- **出图规格**：默认 `n=1` 一张横幅图（1536×1024），prompt 段里强制写明"三视图：正面 / 侧面 / 背面 横向排列"
- 新增文件：
  - `skill/character_turnaround/SKILL.md`
  - `skill/character_turnaround/references/personas/turnaround-expert.md`
  - `skill/character_turnaround/references/prompt-turnaround-zh.md`
- 复用：同 Skill #2

### 4.6 Web UI 扩展

- **角色详情页 tab 切换**：立绘 / 美宣 / 三视图（当前只有立绘）
- **上传按钮**：`POST /api/uploads` → 写 `.runtime/uploads/<temp_id>.png` → 返回 temp_id
- **生成按钮**：每个 tab 角落显示可复制命令字符串，如 `/character-promo holy-spirit-priestess`
- **不做**：直接触发 Skill 的 web → CC 桥接（避免提前抽象）

### 4.7 历代经验自动追加机制

**承载文件**：`references/lessons/<kind>.md`（portrait / promo / turnaround 各一份）

**触发时机**：每次 turn 收尾，满足以下任一条件：
- 出图成功（job → DONE）
- spec 归档（`characters/<id>/spec.md` 写完）
- 出图失败（job → FAILED 且原因明确，比如"prompt 太复杂被截断"）

**Skill 主动询问后追加**（plan-eng-review D2 / 选项 A，refined by §11.2）：Skill 收尾时主动问"要不要把本轮 prompt 经验沉淀一句到 lessons？"，用户答 Y 才追加。详细触发表见 §11.2。
- 一条经验 = 一行 markdown，格式：
  ```
  - YYYY-MM-DD <角色 id> · <一句话决策/教训/亮点> · prompt 片段：`...`
  ```
- 例子：
  ```
  - 2026-05-19 holy-spirit-priestess · 圣光金白配色 + 兜帽阴影遮眼是西幻祭祀的高识别度组合 · prompt 片段：`兜帽低垂遮眼 / 冷光从兜帽内透出`
  ```

**人工微调**：直接编辑 `references/lessons/<kind>.md`，下次 Skill 启动时 `context_loader` 会重新读全文。**不需要重启 server，不需要 reload**。

**故意不做**：
- 不自动总结 / 聚类经验（成本高且容易扭曲原话）
- 不限制条数（前 50 条线性追加；超过 50 条再讨论需不需要分卷归档）
- 不去重（人工微调时如果想合并相似条目，自己改）

**生效路径**：`context_loader.load_lessons(kind)` → 读 `lessons/<kind>.md` 整文 → 拼到专家人设 prompt 前缀，让模型在引导对话时看得到。

## 5. 三种实施路径

### 路径 A：先抽公共层，再加新 Skill（推荐）

| 步 | 内容 | 验证 |
|---|---|---|
| 1 | 角色目录结构迁移：`<id>.md` → `<id>/spec.md` | 现有 Skill 跑通圣灵祭祀对话 |
| 2 | 加 `worldview.md` 模板 + `references/lessons/portrait.md` | 文件存在，SKILL.md 启动步骤加"读 worldview" |
| 3 | 抽 `lib/context_loader.py`、`lib/prompt_builder.py`、`lib/lovart_caller.py` | 现有 character-workflow 仍能跑通 |
| 4 | 加 `JobKind` 枚举 + `source_image` 字段 + 写盘目录分发 | 写一个 PORTRAIT job 跑通 |
| 5 | 加 `/character-promo` Skill | 给圣灵祭祀生成一张美宣 |
| 6 | Web UI 加 promo tab + 上传通道 | 画师能在 web 看到美宣 |
| 7 | 加 `/character-turnaround` Skill | 给圣灵祭祀生成三视图 |
| 8 | Web UI 加 turnaround tab | 三 tab 全通 |

**Effort**: M-L（约 8 步，每步 30 分钟–2 小时）
**Risk**: Low（每步独立可验证）
**优点**：现有 Skill 始终能跑；新增能力可逐步上；抽公共后维护成本低。
**缺点**：第 1-3 步用户感知不强，需要先验证现有 Skill 还能跑。

### 路径 B：先加新 Skill，后抽公共

1. 直接复制 `character_workflow/` 三份，改 SKILL.md 和 prompt 模板
2. 三 Skill 各自独立跑通
3. 再回头抽公共

**Effort**: M
**Risk**: Med
**优点**：用户先看到三 Skill 出图。
**缺点**：代码三份维护痛苦；后续抽公共要改 Skill 内部，回归风险高；prompt 模板版本漂移。

### 路径 C：统一管线

设计 `PipelineSkill` 抽象，所有出图都是 `/character-asset <type> <id>`，参数化 type。

**Effort**: L
**Risk**: High
**优点**：架构最优，未来加卡图/动作/3D 只是加一个 type 配置。
**缺点**：对话模式（专家人设引导）很难统一参数化；现在还没做卡图/动作，过度设计；调试一个 bug 要在 type 分支里找。

## 6. 推荐：路径 A

理由：
- 每步可独立验证，不会出现"做了一半全部不能用"
- 现有 character-workflow 始终可用，画师不会断粮
- 共享 lib 抽出后，未来加卡图/动作/3D 只需复制 Skill 模板 + 改 prompt 模板
- 风险点（角色目录迁移、JobKind 字段扩展）压在前 4 步，越往后越加法不动现有代码

## 7. 落地优先级

**最小可用切片**（满足"三 Skill 套件"的核心承诺）= 路径 A 第 1-5 步：

## 10. 未来扩展：总 Skill（延后项，本轮不做）

用户原始设想里有"最终汇总为一个总的 Skill 按需求调用子 Skill"。本轮不实现，但留接口余地。

### 10.1 为什么延后
- 三 Skill 当前还没各自完善，先做调度层 = 调度一个空架子
- 调度逻辑要靠"做什么"来塑形 —— 等真的有美宣 + 三视图 + 卡图 + 动作四五个 Skill 跑起来，自然能看出调度规律
- 提前做容易过度抽象（参数化分支、type 枚举、配置文件）

### 10.2 现在留的接口余地
为了未来"总 Skill"能优雅地调度子 Skill，三 Skill 都遵守这些约定：

| 约定 | 做法 |
|---|---|
| 统一 CLI 入口 | 每个 Skill 都有 `python -m skill.<name> <subcommand>`，参数风格统一（`<id>` / `--upload <path>` / `--n <int>`） |
| 统一返回结构 | CLI 输出 JSON `{job_id, kind, output_paths, status}`；总 Skill 能直接读 |
| 统一 Job kind 字段 | `Job.kind` 已经枚举化（portrait/promo/turnaround/...），总 Skill 能据此分发 |
| 统一上下文加载 | 都走 `lib/context_loader.py`，不在 Skill 内部 hardcode 路径 |
| 不强制对话 | 子 Skill 接受"完整参数直接出图"模式（绕过对话引导），方便总 Skill 在已确认的情况下一键串联 |

### 10.3 未来总 Skill 的可能形态
（仅记录设想，不当成需求）
```
/character-pipeline <id>
  → 自动判断该角色还缺什么资产（看 characters/<id>/ 目录）
  → 缺 spec 就跑 character-workflow
  → 有 spec 但缺 portrait 就只跑出图环节
  → 缺 promo 就跑 character-promo
  → 缺 turnaround 就跑 character-turnaround
  → 全有了就问"要补哪种新资产"
```

或者更激进的：

```
/character-asset <id> <需求自然语言>
  → 大模型读 lessons + worldview + spec
  → 自己判断要调哪个子 Skill
  → 自己组装参数
```

后者更接近 Agent 化，需要更稳定的子 Skill 基础。**前一种（规则式调度）是路径 A 完成后的合理下一站**。

| 出图成功（Job → DONE） | Skill 主动问"要不要把本轮 prompt 经验沉淀一句到 lessons？"，用户答 Y 则追加；用户跳过/答 N 则不写 |
| spec 归档（写 `spec.md`） | 同上，问"要不要沉淀一句" |
| 出图失败（Job → FAILED） | 仅在 `error` 字段是结构化原因（`prompt 超长` / `模型拒绝` / `内容审核`）时追加；网络抖动等 transient 错误不追加 |
| 用户中途 cancel | 不追加 |
| 同 turn 多次出图 | 每次都问；用户可一次性说"全部不追加" |

**不做自动 LLM 抽取**（避免幻觉污染 lessons）。

### 11.6 lessons / worldview token 预算

- `worldview.md` 软上限 **2000 字**（约 1300 tokens）；超过时 `context_loader` 启动告警
- `lessons/<kind>.md` 软上限 **前 50 条**；超过时建议人工分卷归档
- `context_loader` 加载时打印每文件 char 数到 stderr，画师能感知 prompt 膨胀

### 11.7 lessons 并发写约定

- 单画师 + 单进程假设：同一时间只有一个 Skill 在 turn 收尾追加 lessons
- 实际写入用 `open("a")` 系统级单行 append（POSIX `<PIPE_BUF=4096B` 是原子的，一条 lessons 远小于此）
- 人工微调时如撞上 Skill 追加：以 Skill 写为准，人工再编辑（无锁，靠时序）

### 11.8 cross-skill lib import 路径

- character_promo / character_turnaround 直接 `from skill.character_workflow.lib.context_loader import ...`
- 项目根 `pyproject.toml` 已让 `skill` 作为 package import
- **不抽** `skill/shared/` 或 `skill/common/`（§8 风险表已决策）
- **长期技术债**：character_workflow 一旦改名，三 Skill 全断。等真做"总 Skill"（§10）时再考虑拔到 `skill/common/`

### 11.9 类型签名收紧

- `context_loader` 返回 TypedDict 而不是 magic `dict[str, str]`：
  ```python
  class CharacterContext(TypedDict):
      worldview: str
      lessons: str
      spec: str
      character_id: str
  ```
- prompt_builder 接受 typed object，不容易拼错 key
