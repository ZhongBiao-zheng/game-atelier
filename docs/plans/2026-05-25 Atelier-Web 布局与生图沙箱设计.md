## Problem Statement

当前 Web 只有一个 3 栏画廊 (LeftSidebar + CharacterGallery + SpecForm/ImageDetail), API Keys 用一个浮动按钮 toggle 整页, 没有"主页"概念, 也没有跑 Skill 之外的"散页生图"通道。三个体感问题:

1. **Keys 管理不像产品**: 浮动按钮 + 整页 toggle 是临时方案, 没有进入感, 创建/删除 UX 粗糙。
2. **没有省额度旁路**: 所有出图都走 Skill (Claude/Codex 终端), 当 AI 额度被试图/简单图消耗时, 没有"我有现成 prompt, 直接 API Key 出图"的低成本通道。
3. **回到工具时没有 home**: 打开 Web 直接落到 3 栏画廊, 缺一个"工坊全景"的视觉锚点 —— 既是用户重进点, 也是未来 OSS 用户认识这个工具的"脸"。

## What Makes This Cool

把原本看似对抗的"Web 自由生图"和"Skill 经验沉淀"扭成**双向喂养**:

- **Skill → Web**: spec.md 提供 system prompt 上下文（试稿时仍能站在角色定位上放飞)
- **Web → Skill**: 收藏图是"画师亲自验证过好看"的样本, Skill 启动时从这些样本反哺出"什么样的描述方式产生什么样的画面 vibe", 沉淀为去角色化的 prompt engineering 经验

这不是简单的"加生图页", 是给项目独有的经验沉淀机制接上一个"养料管道"。

## Constraints

- 项目本质是 Skill (终端为主, Web 为辅), Web 不能反客为主, 不能把 Skill 边缘化
- DESIGN.md "Atelier" 暖调暗色画廊美学是硬约束, 不能为做 dashboard 风让步
- 文件系统是 single source of truth, Web 不能写 spec.md / 角色档案
- viewer-server 绑死 127.0.0.1, 共享 web tab 仅 1 个
- 未来要扩展视频出图, 现在做的生图壳必须能复用
- 内部自用 + 未来 OSS, 需要 URL 可分享 + 文档化友好

## Premises

1. **生图页定位 = 草稿场 + 反哺池**, 不绑角色, 不直接写 spec.md。功能上是"省 Claude/Codex 额度 + 试探 prompt 的旁路"。

2. **桥设计**: 收藏按钮 → 收藏池存到 `<data_root>/favorites/`。Skill 启动时, 当**未提炼收藏 ≥ 3 张（可配）才询问** 是否提炼, 或用户主动 `/提炼-favorites` 触发。不每次必问 —— 否则会变 Enter 跳过的噪音。

3. **提炼经验只落 `<data_root>/MEMORY.md::prompt_patterns`**, 去角色化, 只记"怎么写 prompt 出好结果"。
   - spec.md = 角色档案
   - MEMORY.md = prompt engineering 经验
   - 两件事彻底解耦

4. **架构延展性**: 生图 / 生视频共享同一个对话流 shell, 分歧在 `kind: "image" | "video"` + `params`。共用 `JobSubmit` 的 schema, prompt 输入 + 历史浏览组件可复用。

5. **路由壳**: 引入轻量 client-side route (`wouter` ~3KB)。四个 zone:
   - `/` → Atelier 主页 (default landing)
   - `/studio` → 生图沙箱 (未来 `/studio?kind=video` 扩视频)
   - `/character/:id` → 现 3 栏
   - `/settings/keys` → Keys 页 (废除浮动按钮)

6. **Atelier 主页 = 画廊作品集**, 不是 dashboard, 不堆 metric, 不放"今日 N 张/M 未读"小入口条。

7. **左上角"Atelier" 是 home 锚点**, 任何 zone 都能点回。这也是 OSS 用户认得这个工具的脸。

8. **现有 API Keys 浮动按钮 toggle 作废**, Keys 进 `/settings/keys` 路由, 头部 nav 提供入口。

## Approaches Considered

### Approach A: Minimal Viable
在现有 `useState` view enum 基础上加 4 个 zone, 不引新库, 不做收藏池。1-2 天能合。Pros: 风险低、快。Cons: 收藏-反哺核心解锁推迟, 没 URL 不能分享, 主页画廊数据粗。

### Approach B: Ideal Architecture ✅ 选定
引入 `wouter` 路由 + 立完整 4 zone + 收藏池 + Skill 反哺端点, 一次性把"省额度旁路 + prompt 经验沉淀"闭环立起来。OSS 友好。

### Approach C: Lateral ("一间屋子, 不切页")
不分路由, 整个 Web 是一个画廊空间, 状态以 Framer Motion transition 表达, Cmd+K palette 控制切换。视觉极独特但实现成本高、user mental model 陌生、OSS 文档难写。

## Recommended Approach: B

### B.5 收藏池 + 反哺 Skill

**后端新增**:

```
<data_root>/favorites/
├── index.json              # 收藏元数据 (job_id, prompt, model, params, ts, 是否已提炼)
└── <job_id>/
    └── original.{png,jpg}  # 软链或拷贝, 看实现, MVP 用 hard copy
```

`index.json` 结构:
```json
{
  "version": 1,
  "items": [
    {
      "favorite_id": "fav-...",
      "job_id": "job-...",
      "kind": "image",
      "prompt": "...",
      "model": "gpt-image-2",
      "params": {"size": "1024x1024", "ratio": "1:1"},
      "image_path": "favorites/fav-.../original.png",
      "favorited_at": "2026-05-25T11:00:00Z",
      "distilled_at": null  // null = 未提炼, ISO ts = 已提炼
    }
  ]
}
```

**REST 端点 (viewer_server/routes.py)**:
- `GET /api/favorites` → 返回 index.json
- `POST /api/favorites` body `{job_id}` → 加进 index, 拷图到 `favorites/<fav_id>/`
- `DELETE /api/favorites/<favorite_id>` → 移出
- `GET /api/favorites/undistilled-count` → 给 Skill turn-start 用

**Skill 端 (src/character_workflow/)**:
- 新建 `lib/favorites.py`:
  - `list_favorites(undistilled_only=False) -> list[FavoriteItem]`
  - `mark_distilled(favorite_ids: list[str])`
- 修改 `turn-start` 输出: 在现有 `{drafts, active_id, spec}` 上加 `lessons_pending_count: int` (= 未提炼收藏数)
- Skill 在 stage D 检测 `lessons_pending_count >= 3` 时, 在 stage D context 末尾 emit 一条提示:
  ```
  💡 你有 5 张收藏图未提炼为 prompt 经验。要现在提炼吗 (y / 跳过)?
  ```
- 用户答 y → Skill 跑提炼:
  1. 拉 favorites (含 prompt + image)
  2. 调 LLM 用这个 prompt:
     ```
     看以下这 5 张图 + 对应 prompt:
     [图1] prompt: "..."
     [图2] prompt: "..."
     ...
     从这些"画师认可"的样本里, 总结出 3-5 条 prompt 写作经验。
     输出格式: 一条经验一行, 不超过 50 字。
     ```
  3. 经验追加到 `<data_root>/MEMORY.md` 的 `## prompt_patterns` 段（已存在就 append, 没有就建）
  4. 提炼完 `mark_distilled([...])`
- 也提供 CLI: `uv run python -m character_workflow distill-favorites`

**MEMORY.md 段示例**:
```markdown
## prompt_patterns

- 描述材质用 "soft cotton + matte finish" 比 "fabric" 出图更稳
- 镜头描述放最前: "low-angle, dramatic" 比放在末尾权重高
- 暖色调统一用 "warm tungsten lighting" 避免被冷化
```

## Open Questions

1. **wouter vs react-router**: 选 wouter 是 OSS 友好（小依赖）+ API 简单。如果你倾向更主流的 react-router, 实施时换掉, 改动量极小（API 几乎兼容）。
2. **收藏图存放方式**: hard copy 还是软链？MVP 用 hard copy 简单可靠, 后期空间紧可换 symlink + 引用计数。
3. **Studio kind 切换的 URL 表达**: `/studio?kind=image` 还是 `/studio/image`？前者轻量, 推荐前者。
4. **提炼经验时是否给用户预览**: AI 输出经验后, 直接写入 MEMORY.md 还是先在终端展示让用户 y/n 每条？倾向后者（保留用户审核权）, 但提炼流程会长一点。
5. **如果同一张收藏图已经在 spec 里出现过怎么处理**: 不去重, 收藏池只看自己, 提炼也独立运行（去角色化）。
6. **未读反馈在哪里露出**（你说不在主页）: 倾向放在 LeftSidebar 的角色名右边角标 + Skill turn-start 输出。
7. **Atelier 标志的具体字符**: 就用文本 "Atelier" Instrument Serif 还是要做个 logo SVG？MVP 用文本, OSS 上线前可考虑加 mark。

### A. 架构 (4 关键 findings)

**A1. `JobKind` 语义冲突 — 阻塞 / 必修。**
- 现状: `JobKind = PORTRAIT/PROMO/TURNAROUND` 含义是"角色目录下的资产槽位"，决定 `characters/<id>/<kind>/` 的物理路径 ([src/character_workflow/lib/jobs.py:24](src/character_workflow/lib/jobs.py#L24-L27))。
- 设计稿 §B.4: `JobKind = IMAGE/VIDEO` 含义是"媒体类型"。同字段，两套含义，不能并存。
- **推荐**: 新增独立字段 `media_kind: MediaKind = IMAGE`，保留 `kind: JobKind` 表示槽位。Studio standalone 用 `kind=PORTRAIT`（或新增 `STUDIO`）+ `media_kind=IMAGE`；未来视频改 `media_kind=VIDEO`。槽位与媒体解耦后，"video portrait" / "video promo" 都能合法表达。
- **替代**: 重命名 `JobKind → AssetSlot` + 新建 `JobKind = IMAGE/VIDEO`。语义更干净但迁移面大（已有 5+ 角色 job json 都要兼容反序列化）。
- **测试**: 加 regression test —— 老 `{"kind":"portrait"}` job json 反序列化后 `kind == JobKind.PORTRAIT, media_kind == MediaKind.IMAGE`，不抛错。

**A2. `character_id: str` → `Optional[str]` 破坏不变量 — 阻塞 / 必修。**
- 现状: 这是 `Job` 模型核心字段（[schemas.py:48](src/character_workflow/lib/schemas.py#L48)），下游硬依赖:
  - `job_output_dir(character_id, kind)` 拼路径 ([jobs.py:24](src/character_workflow/lib/jobs.py#L24))
  - `job_runner.run_job` 写文件目录 ([job_runner.py:201](src/character_workflow/lib/job_runner.py#L201))
  - `routes.py /api/images` 按 character 过滤
  - `watcher.py` ImagesHandler 按 character 目录分发 SSE
- **推荐 (sentinel)**: `character_id: str` 保留**非空**, 引入常量 `STUDIO_NAMESPACE = "_studio"`. Studio 标准出图写 `character_id="_studio"`, 输出落到 `<data_root>/_studio/<job_id>/v1.png`. 优点: 不动 schema 类型, 不动 24 处 `character_id`-touching 代码; Web 只要在过滤 character 列表时排除 `_studio` 前缀; SSE / watcher 自动复用。
- **替代 (Optional)**: 改成 `Optional[str]`. 优点: 类型表达准确; 缺点: 所有下游要补 None 分支, 测试面 + 出错面都扩大。
- **测试**: regression — `list_jobs()` 含 studio job 时不崩, `routes.py /api/characters` 不返回 `_studio`, `job_runner.run_job` 对 studio job 落到正确目录。

**A3. wouter 客户端路由 + FastAPI 静态挂载: SPA fallback 必须显式。**
- 现状: `viewer-server` 把 `web/dist` 静态挂载, 用户在 `/character/foo` 上**刷新浏览器** → FastAPI 不认识 `/character/foo` → 404, 不会落到 `index.html`. wouter 不会自己解决服务端路由问题。
- **修**: `server_app.py` 加 SPA fallback —— 所有非 `/api/*` 和非静态资源前缀的 GET 都返回 `index.html`. 这是 wouter / react-router 都需要的标配, 但设计稿没写。
- **测试**: 集成测试 — `curl http://127.0.0.1:5174/character/foo` 返回 `index.html` (200) 不是 404。

**A4. 收藏池竞态 — 高严重度（命中既有 learning `draft-file-race-condition-atomic-rename`, 9/10）。**
- 现状: 设计稿 §B.5 写 `mark_distilled(favorite_ids: list[str])`. 如果**画师在 Skill 提炼期间又收藏了新图**:
  - 若 `mark_distilled` 写"全部当前 undistilled"模式 → 新收藏被错标 distilled (永久错过提炼)
  - 若设计成 fav_id 白名单模式但 Skill 用 `list_favorites(undistilled_only=True)` 拿到的快照, 写回 `index.json` 时被新收藏覆盖 → Skill 写丢
- **修**:
  1. Skill 取快照: `frozen_ids = [f.favorite_id for f in list_favorites(undistilled_only=True)]`
  2. 喂 LLM 完后: `mark_distilled(frozen_ids)`, 严格按 id 写而非"全部 undistilled"
  3. `index.json` 落盘必须 atomic rename (`tmp.replace`), 不能 in-place write
  4. POST `/api/favorites` 也走 atomic rename, 读改写在内存里
- **测试**: 写一个并发测试 —— mock `list_favorites` 在中间加新条目, 验证 `mark_distilled` 只标 frozen 集合, 新条目仍是 undistilled。

### B. 代码质量 (3 findings)

**B1. App.tsx onboarding 分叉 vs AppShell 路由 — 共存策略不清晰。**
- 现状: `App.tsx` 根据 `OnboardingState.status` switch 到 `DataRootPage` / `KeysPage(mode=onboarding)` / `MainApp`. 引入 wouter 后, onboarding 阶段**不能**挂 `<Switch>`, 否则用户在 needs_first_key 状态下 `/character/foo` 不再被 KeysPage 拦截。
- **修**: `App.tsx` 保留 onboarding 分叉; **只在 `ready` 分支** mount `AppShell + <Switch>`. 设计稿应明写这一层守卫, 否则 onboarding 用户会被路由器抢走。

**B2. Studio 用现有 `POST /api/prompt/{job_id}` 不够 — 需新端点。**
- 现状: `WebEditableJobPatch` 白名单只允许 `prompt/model/params/seed`. Studio 第一次提交需要写 `character_id / kind / alias / provider`, 不在白名单里 ([schemas.py:65-70](src/character_workflow/lib/schemas.py#L65-L70))。
- **修**: 新增 `POST /api/studio/jobs` body `{prompt, model, params, alias, media_kind?}` → 服务端写 `character_id="_studio"`, `kind=...`, 走标准 `write_job → confirm → run_job` 链路。**这条不写白名单, 由服务端默认**, 维持 "Web 不能改 job 状态字段" 的硬约束。
- **测试**: API 测试 — POST `/api/studio/jobs` 创建出 `status=pending_confirm` 的 job, character_id="_studio", `/api/jobs/{id}/confirm` 推到 pending, runner 跑完落 `<data_root>/_studio/...`。

**B3. `keys.preferred_alias_for_kind("image")` 当前返回 None — Studio 默认 key 行为未定义。**
- 现状: 该函数只识别 `portrait/promo/turnaround` ([keys.py](src/character_workflow/lib/keys.py))。Studio kind=image 进来, 返回 None → Studio UI 必须强制画师手选 key, 没法"用 default 出图"。
- **修**: Studio 端不要走 `preferred_alias_for_kind`, 直接读 `keys.read_keys_db().default_alias`. 这个语义本来就是"哪个 alias 是默认"而不是"哪个 alias 给哪种资产"。Skill 用前者, Studio 用后者, 互不冲突。
- **测试**: Studio API 不传 alias → 自动用 default_alias; 传 alias → 优先用传入的。
